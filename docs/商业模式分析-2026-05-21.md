# QuantumClaw 商业模式分析 — 2026-05-21

## 现状：API 中继工具 → 不是平台

QuantumClaw 当前是纯技术代理工具，商业模式为零：

| 角色 | 现状 | 问题 |
|------|------|------|
| 平台方 | 有渠道管理、利润分析 | 看得到利润数字但收不到钱 |
| 供应商 | 渠道无归属（无 user_id） | 第三方无法入驻 |
| 消费者 | 用 Token + 抽象额度 | 额度免费送，不花钱 |
| 收入 | 0 | 平台垫付所有上游成本 |

## 目标：平台 + 入驻商家模式

```
供应商（有 API Key）入驻
  → 配置自己的渠道（CostPerUnit + SellPriceRate）
  → 消费者调用供应商的渠道
  → 平台抽佣 + 供应商赚钱
```

## 收费模型（最终确认）

**两层叠加，总平台抽成 ≈ 6%**

| 收费层 | 比例 | 什么时候扣 | 说明 |
|-------|------|-----------|------|
| 交易抽成 | **1%** | 每笔 API 调用即时扣 | 覆盖通道费+运维 |
| 入驻费 | **5%** | 提现时按总营业额结算 | 赚钱后收，先算清再提 |
| **合计** | **≈ 6%** | — | 供应商净得 ~94% |

**入驻免费**，零门槛。

### 入驻费计算口径
- 按**渠道总营业额**（消费者付的钱），不是按利润
- 默认**每月**一个结算周期
- **提现时先扣入驻费**——把当前周期到当天为止的总营业额 × 5% 算清，再允许提现

### 一个完整数据流

```
消费者付 ¥100 调用 API
  ├─ 交易抽成 1% → ¥1 (平台即时入账)
  └─ ¥99 进供应商收益 (pending 状态)

供应商成本（上游 API Key）：¥60
供应商账面毛利：¥40

月底/提现时：
  本月总营业额 = ¥10,000
  入驻费 = 5% × ¥10,000 = ¥500
  供应商累计可用 = ¥9,900
  扣除入驻费后 = ¥9,400
  减去上游成本 = ¥9,400 - ¥6,000 = ¥3,400 净利润

平台总收入 = ¥100(交易) + ¥500(入驻费) = ¥600
```

### 入驻费结算规则（三条铁律）

**规则一：提现时必须结算**
供应商提现时，先算清所有未结入驻费，扣完再提。

**规则二：不提现按月自动结算**
整月无提现操作 → 次月 1 号系统自动扎帐，记录入驻费应扣金额（不实际操作余额，等下次提现时统一扣）。

**规则三：当月总营业额 < ¥100 → 该月跳过，不处理，不累计**
每个结算周期独立算，当月营业额不够门槛就整月跳过，不累计到下月。
- 场景 A：1月营业额 ¥80 < ¥100 → 跳过，1月入驻费 = ¥0
- 场景 B：2月营业额 ¥120 ≥ ¥100 → 按 2 月营业额算入驻费 = ¥120 × 5% = ¥6
- 场景 C：提现时入驻费按已结算的月份扣，跳过月份不补

#### 周期边界场景

| 场景 | 处理 |
|------|------|
| 刚开张就提现 | 按本周营业额 × 5% 扣 |
| 月中提现 | 算当月 1 号到今天 × 5%，减去已扣部分 |
| 整月不提现 | 挂账，下月提现时两月一起算 |
| 收益不够扣入驻费 | 提示无法提现 |

## 改造范围（5 大模块）

### 一、数据模型改动

**1. Channel 表加字段**
- `user_id` int — 渠道归属（0=平台，>0=供应商）

**2. 全局配置（OptionMap）**
- `platform_commission_rate` → 1.0（交易抽成 %）
- `platform_fee_enabled` → true（入驻费开关）
- `platform_fee_rate` → 5.0（入驻费 %）
- `platform_fee_period` → monthly（结算周期）
- `platform_fee_tiers` → 阶梯费率（可选，以后扩展）

**3. 新增表**
- `platform_fee_records` — 入驻费结算记录
  - id, user_id, channel_id, period(YYYY-MM), total_revenue,
    fee_rate, fee_amount, deducted_at, status(pending/deducted)
- `withdrawal_requests` — 提现申请
  - id, user_id, amount, platform_fee_deducted,
    net_amount, status(pending/approved/rejected/completed),
    bank_info, created_time, processed_time

**4. User 表语义变更**
- `Quota` → 改为真实货币余额（单位：分），不再是抽象额度

### 二、权限改造

- 渠道管理开放给**所有登录用户**
- 每个用户只能看/改/删**自己的渠道**
- 管理员看全部渠道 + 管理供应商

### 三、计费改现金

- 消费者注册送微量试用金（如 $1，替代 QuotaForNewUser）
- 消费者充值（Stripe 等）→ 余额增加
- API 调用 → 扣余额（不是扣抽象额度）
- 保留现有额度体系作为**现金的映射**（1 额度 = 固定计价锚）

### 四、分账逻辑

```
API 调用成功 →
  消费者扣款 ¥100
  平台交易抽成 ¥1（即时入账平台）
  供应商收益 ¥99（pending → settled）

提现时 →
  算入驻费 = 总营业额 × 5% - 已扣入驻费
  从供应商可提现额中扣除
  剩余部分打款给供应商
```

### 五、供应商端 + 管理后台

**供应商能看到：**
- 我的渠道（CRUD）
- 收益看板（总流水、平台抽成、入驻费、可提现）
- 提现申请

**管理员能看到：**
- 供应商列表 + 审核
- 各供应商入驻费明细
- 提现审核（通过/拒绝）
- 平台财务总览

## 实施节奏建议

```
第一刀（核心闭环）：
  Channel.user_id + 消费者余额充值扣款 + 交易抽成 1%

第二刀（供应商体系）：
  供应商管理自己的渠道 + 收益看板

第三刀（入驻费）：
  入驻费 5% 月度结算 + 提现时扣费

第四刀（管理后台）：
  供应商审核 + 提现审批 + 财务看板
```

第一刀跑通就能形成「消费者充值 → 调用 API → 平台抽佣 → 供应商赚钱」的闭环。
